Remediation plan 08

P0 and P1: the right next investments

Prioritize operational proof and reliable delivery over more surface-area features. Each work item is framed as a measurable acceptance decision—not a vague improvement intention.

P0
Close the unsafe boundaries
Required before describing the backend as operationally reliable.
Complete environment contract
Inventory server, client, OAuth and deployment variables in one validated interface.
ACCEPTANCE: no undocumented required variable; startup failure path is tested.
Make the provider boundary explicit
Either implement signed provider delivery or disable the simulated worker by default and label it a scaffold.
ACCEPTANCE: no documentation or runtime path can imply simulated success is real delivery.
Define delivery ownership
Specify who owns credentials, retry policy, failure escalation and event-schema changes.
ACCEPTANCE: provider contract and operational owner are documented.
Protect production claims
Keep demo, validated and production-only statements distinct in README and audit material.
ACCEPTANCE: reviewer can map every major claim to code or evidence.
P1
Build operational proof
The next tranche converts sound design into runtime evidence.
Atomic event claim and lease recovery
Use conditional claim semantics, a lease deadline and recovery of stale processing work.
ACCEPTANCE: multi-worker test proves one active claim per event.
Real MySQL/MariaDB concurrency suite
Run parallel idempotent requests in CI against an ephemeral database engine.
ACCEPTANCE: single business effect, duplicate response and lock-error policy asserted.
Operational telemetry and dead-letter policy
Add structured logs, worker readiness, backlog age, failed-delivery metrics and recovery workflow.
ACCEPTANCE: health/alert dashboard has owner and runbook.
Expand CI quality evidence
Add lint, dependency scanning, release smoke checks and targeted browser E2E.
ACCEPTANCE: GitHub required checks reflect the release risk profile.
Investment decision
Do not add a separate Python service merely for appearance. First harden the existing TypeScript service boundary, prove database and delivery semantics, then introduce an interoperable Python worker/API only where a concrete workload justifies it.

Priority labels reflect operational risk and evidence gaps identified in the current audit; they are not a claim that all listed controls are already implemented.
