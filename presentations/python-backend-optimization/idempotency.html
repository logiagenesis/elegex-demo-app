Idempotency design needs real-DB proof

The architecture places duplicate prevention at the database boundary—a sound direction. The remaining work is to prove the exact locking and failure behaviour against the actual MySQL/MariaDB engine.

01 / CLIENT
UUID per queued action
The IndexedDB queue assigns a stable idempotency key before retry or replay.

02 / SERVER

Protected procedures derive organisation scope from authenticated membership.

03 / DATABASE
Composite uniqueness boundary
Organisation and idempotency key are handled within the transaction path.

04 / EVIDENCE GAP
Real engine race is unproven
The current concurrency test is mocked, not an InnoDB integration run.
Current evidence supports the design
✓
Stable replay key: a UUID persists with the queued browser action and crosses the tRPC boundary.
✓
Server-owned tenancy: the client does not submit organisation scope as an authority.
✓
Database-first duplicate control: unique-key handling avoids trusting an application-only cache.
✓
Stress scenario: a mocked 50-request concurrent idempotency simulation passes.
Production proof still required
!
Ephemeral MySQL/MariaDB CI job: exercise real transaction and unique-index behaviour.
!
Parallel request test: assert a single business effect under genuine contention.
!
Deadlock and lock-wait policy: assert retry/error handling rather than assuming happy-path atomicity.
!
Authenticated browser E2E: validate the full queue → server → database replay path.
Why the distinction matters
InnoDB uses row-level shared/exclusive locks and conflicting transactions can wait. A mock validates application intent; only a real-engine test validates the interaction with those database semantics.

Source: repository idempotency tests and database workflow code; MySQL 8.0 Reference Manual, “InnoDB Locking.”
