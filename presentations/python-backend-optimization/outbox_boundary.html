Backend reliability boundary

Outbox: honest boundary, not Celery parity

The repository contains a useful durable-outbox direction, but its current worker is a polling demonstration—not a production-grade external-delivery service.

Current worker
Polls active connections, selects ready events, updates status and attempts, and applies retry backoff. Its successful delivery path is simulated.
Implemented control surface
✓
Durable event records exist in the integration-event store.
✓
Status and attempt counters record basic processing state.
✓
Retry backoff reschedules failures up to a local attempt limit.
✓
Worker lifecycle hooks start and stop an in-process poller.
✓
Explicit code comment now identifies simulated delivery as a demo limitation.
Required for production dispatch
!
Provider adapter and signed delivery are absent; no webhook/API call is made.
!
Atomic conditional claim is absent; concurrent workers can race after selection.
!
Lease expiry and recovery are absent for events stuck in processing.
!
Timeouts, dead-letter operations and metrics are not implemented.
!
Separate worker deployment and health/SLO controls are not implemented.
Required positioning: describe this as an engineering showcase of a durable-outbox pattern. Do not describe it as completed webhook/API integration or as a Celery-equivalent worker platform.
Source: current repository worker and outbox implementation; recommended operational controls align with SRE-style measurable service ownership.
