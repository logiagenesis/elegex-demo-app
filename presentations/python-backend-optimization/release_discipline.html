Operating model 09

Corporate release discipline keeps GitHub and evidence aligned

The release process should make each deployable change traceable from a fresh clone through a required remote check, then measure the service behaviours that matter after deployment.

01 / SOURCE
Fresh clone
Start from an immutable commit on origin/main.
→
02 / QUALITY
Deterministic verify
Frozen install and one integrated local gate.
→
03 / REVIEW
Reviewable change
Small, attributable change set with explicit scope.
→
04 / REMOTE
Required GitHub check
Push only integrated code; verify the remote Quality run.
→
05 / OPERATE
Health and rollback
Recommended next control: observed service health governs release pace.
Controls that make reviews credible

Evidence before approval

✓
Protected quality gate: formatting, type checking, tests and build run as a single release command.
✓
Remote confirmation: the GitHub Actions Quality workflow must pass for the exact pushed commit.
✓
Safe deployment record: migrations, rollback criteria and health checks should accompany every operational release.
Next operational control

Track a small set of meaningful indicators

Google SRE recommends selecting a limited set of service indicators tied to user outcomes—not every metric available.

Request success rate
Detects user-visible failures.
p95 latency
Shows tail user experience.
Outbox backlog age
Reveals stalled background work.
Failed delivery count
Shows provider/integration stress.
Idempotency conflict rate
Checks replay and client retry behaviour.
Operating principle: do not equate a successful push with a successful release; measure the integrated commit in GitHub, then monitor the service behaviour it creates.
