# Staging Runbook

This runbook describes the repository workflow for an external staging deployment. The in-product **Staging readiness** screen deliberately shows synthetic release evidence so the expected control surface is visible in the demo; it does not replace the real checks below.

## Environment contract

| Environment | Purpose                | Data rule                                       | Promotion rule                                  |
| ----------- | ---------------------- | ----------------------------------------------- | ----------------------------------------------- |
| Development | Local feature work     | Local or disposable tenant data only            | Unit tests and type checks pass                 |
| Staging     | Candidate verification | Synthetic or approved non-production data only  | Migration reviewed; smoke paths complete        |
| Production  | Live customer workload | Real data; backups and least privilege required | Change approved and rollback reference recorded |

## Release sequence

1. Create and review an additive Drizzle migration: `pnpm drizzle-kit generate`.
2. Read the generated SQL. Do not apply destructive changes without a backup and a reviewed rollback plan.
3. Apply the migration in staging with the database tooling for the hosting platform.
4. Run `pnpm verify`, then exercise the OAuth sign-in, tenant isolation, job register, dispatch, document upload, report export, and administrator routes.
5. Record the candidate version, source commit, deployment time, health outcome, and known rollback version in the release record.
6. Promote only after staging checks pass; repeat the production smoke test with approved credentials.

## Minimum staging checks

| Category      | Check                                                                         | Evidence                                     |
| ------------- | ----------------------------------------------------------------------------- | -------------------------------------------- |
| Database      | Migration is additive and schema matches application types                    | Reviewed SQL and successful migration output |
| API           | Tenant-scoped procedure calls reject unauthenticated or unauthorized requests | Automated authorization suite                |
| UI            | Dashboard, jobs, dispatch, reports, documents, and admin routes render        | Browser smoke record                         |
| Security      | No credential has been committed; secrets remain in host configuration        | Secret-manager review                        |
| Storage       | Upload rules reject unsupported size/type and document URLs resolve           | Scoped upload test                           |
| Observability | Connector health and application logs have no release-blocking errors         | Health probe and deployment logs             |

## Rollback

Use the hosting platform’s version history to restore the prior known-good application version. Do **not** use ad-hoc destructive Git or SQL commands as an application rollback. Database rollback requires an explicit reviewed migration plan; additive migrations should be preferred so application rollback does not require data loss.

## Synthetic-demo disclaimer

The release rows and check evidence generated by the demo seed are demonstration records. They model a release-control process but are not proof that an external deployment has passed those checks.
