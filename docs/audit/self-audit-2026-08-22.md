## Managed database recovery and migration evidence

The managed deployment workspace was imported from GitHub revision [`e3440df`](https://github.com/logiagenesis/elegex-demo-app/commit/e3440df) after that revision passed the `Type, test, and production build`, CodeQL `Analyze`, and `Repository secret scan` checks. Its database initially contained only the base `users` migration and three empty partial tables left by a failed manual migration attempt. Before changing schema, a logical rollback snapshot was created inside the managed database at **2026-08-22 12:47:07 UTC**: `release_backup_20260822_1238_users`, `release_backup_20260822_1238_migrations`, and `release_backup_20260822_1238_manifest`. The manifest records zero user rows, one migration-ledger row, and zero rows in each quarantined partial table; read-back checks matched those counts.

After explicit user authorization, the matching base-migration ledger timestamp was corrected from the platform-created value to the committed `0000_gifted_forge` timestamp. The ordered Drizzle runner then recorded **12** migrations through `0011_cold_namora`. Schema inspection confirmed all nine startup-guard columns and eight intended foreign-key constraints. The imported application subsequently started and its unauthenticated managed-preview entry page rendered. This is **PARTIAL** deployment evidence only: the logical snapshot is not an off-platform disaster-recovery export, the workspace has not been published, and no authenticated workflow smoke test has been completed.
